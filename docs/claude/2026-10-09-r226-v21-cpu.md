# The r226 v21 build on 120 cores: CPU use and efficiency

Date: 2026-10-09.

Data: the r226 v21 build's share archive (`local/v21/protal0.7.9_r226_v21`; SLURM job 24112881, `-t 120`, a node with
1.5 TB of memory, `--scratch` on the node's SSD with 527 GB free, the inputs and OUTDIR on `/hpc-home`). It was built
with the scripts at `7ace9b8` and protal at `ea6de54`. v19 (`local/v19`, SLURM 24099010, `-t 84`, a node with 502 GB) is
used for comparison.

Method: read-only, from the logs. The protal-run timings come from
[`2026-10-09-build-parallelism/scripts/run_timings.sh`](2026-10-09-build-parallelism/scripts/run_timings.sh); the rest
are greps and short perl sums, listed under Reproducing.

**Question.** How is the build doing on CPU use and efficiency at 120 cores?

## No CPU logs in this build

v21 predates the CPU logs. It ran at `7ace9b8` (scripts) and `ea6de54` (protal), and the logs came with `79ae8ee`. So
its archive has no `logs/cpu_jobs.tsv`, `logs/cpu_timeline.tsv`, `logs/protal_cpu_<collection>.tsv` or protal
`misc/cpu.tsv`, and nothing in it records CPU time. Today's other changes are not in it either: the ONT indel bound,
`--profile-ahead` on by default, the setup graph, the parallel derive, the genome cache, the early reports and the
merged streamed runs.

What follows is reconstructed from step and stage timers. Where the cores were busy and where they idled is **inferred**,
mostly from how fast the finished database's idle-priority build progressed (section 3). The next build's CPU logs will
measure it.

## Summary

v21 took **3:15** (ready after 3:00), against v19's 3:49 (ready 3:31) on 84 cores: **−15%** for 43% more cores.

| Part | v19 (84) | v21 (120) | Change | What limits it |
|---|---|---|---|---|
| Setup to the training database | 40:24 | **53:10** | +32% | NFS reads and serial steps: the converter 4:04 → 7:23, gene neighbours 3:18 → **15:37**; only the training database build (12:37) uses the machine |
| Collection (both) | 2:45:47 | **2:00:57** | −27% | six protal runs back to back, 2:00:01 of protal in 2:00:57; ONT 63% of the aligning |
| Training to "Ready" | 4:28 | 4:47 | | four trainers × 30 threads |
| Reports | 18:10 | 15:14 | −16% | contig names from NFS (6:01), four single-threaded ancestry passes |

1. **The collection scaled about as the cores did** (−27% against the ideal −30%). Its protal runs kept the machine
   busy: the finished database, built beside them at the idle scheduling class, ran 7-15× slower than alone, so the
   runs left only ~8-17 of the 120 cores idle on average (section 3).
2. **But the read types scaled very differently:**

| Read type | v19 aligning | v21 aligning | Speed-up (cores: 1.43×) |
|---|---|---|---|
| ONT | 6,001 s | 3,777 s | **1.59×** |
| PacBio | 1,112 s | 879 s | 1.27× |
| paired-end | 902 s | 765 s | 1.18× |
| single-end | 571 s | 583 s | **0.98×** |

   Short reads gained little or nothing from 36 more cores, while the cores stayed busy. That points to memory
   bandwidth or latency (the seeding's random reads of a ~35 GB index, possibly across NUMA nodes) rather than idle
   cores. The node also differs, so this is not a clean scaling test.
3. **ONT is 63% of the aligning** (3,777 of 6,005 s) and compute-bound. The indel bound committed today (`0c94366`,
   −45% of the alignment step's instructions on the bench sample) is the largest lever left.
4. **The setup got slower** despite more cores: its NFS-bound steps vary 2-5× between builds. Gene neighbours read
   37,331 genomes in 15:37 here against 49,405 in 3:18 in v19.
5. **Smaller losses inside the collection:**
   - the profiling stages, 14.4 min (12% of the protal time), each bounded by its slowest samples, whose profiling grew
     41% since v19;
   - streamed paired-end samples aligning ~30% slower than written ones (the simulator runs on 120 threads beside
     protal's 120);
   - small samples, ~3.5 min;
   - start-ups, ~3 min.

**With today's commits** (`79ae8ee`, `0c94366`), the same build should take roughly **2:15-2:35**. One new risk: the
finished database's idle-priority build (1:59 here) ended only 3 min before the collection. A collection 30-50 min
shorter would leave part of that build on the critical path (section 6).

## 1. Where the 3:15 went

| Step | Wall | Cores used (inferred) |
|---|---|---|
| genome table (37,422 genomes from `/hpc-home`) | 8:00 | a process pool reading NFS |
| converter | 7:23 | serial Python and zstd: marker genes spooled 61 s, `reference.fna` written 118 s, the full reference's 173 chunks 132 s, joined 69 s |
| gene neighbours (after the converter, at `7ace9b8`) | 15:37 | a pool reading every genome from NFS |
| species clouds | 0:09 | all |
| in-silico strains | 2:23 | few |
| training database: its files derived | 6:42 | one process (`7ace9b8`) |
| training database: the build | 12:37 | all: congener gaps 8:14, the index ~2 min, writing 1:17 |
| collection | 2:00:57 | protal, 86-93% busy (section 3) |
| training (4 trainers × 30 threads) | 3:28 | all |
| parity, composition, models added | 1:07 | few |
| reports | 15:14 | contig names 6:01 (NFS), error reads 2:43, unpack 1:33, ancestry ~5 min (four single-threaded processes) |

About **57 min of the 3:15 ran on few cores**: the setup but its training build (40:24), the reports (15:14) and
the checks before "Ready" (1:19). The 2:00 of the collection ran on most of them.

## 2. The collection: six protal runs, back to back

From the two collections' logs, the runs went in this order:
- the test set's streamed run (21:43);
- training run 1, streamed (31:19);
- the test set's written run (16:06);
- training run 2, written (29:38);
- training run 3, streamed (18:06);
- training run 4, streamed (3:09).

That is 2:00:01 of protal in a collection of 2:00:57. The protal lock was never free, and the simulations ended at 12:32,
13 min into the collection. Training run 1 waited ~21 min for its turn. It had chosen its batch before the wait, which
the collector no longer does (`79ae8ee`); the wait cost nothing here, as the lock was busy all along.

Inside the runs (seconds, both collections):

| | Seconds | Share of protal time |
|---|---|---|
| aligning | 6,005 | 84% |
| profiling stages | 866 | 12% |
| start-ups (index, preload, tables) | ~190 | 3% |

**Aligning by design point** (`run_timings.sh`):
- ONT runs at 6,900-7,900 reads/s at 120 threads, against 4,300-4,800 at 84 (+20% per thread: a faster node, or less
  contention).
- Paired-end:

| Sample | Pairs/s at 120 threads | At 84 threads (v19) |
|---|---|---|
| `sc_gut_pe` | 0.98M | 0.80M |
| `sc_soil_pe` | 1.12M | 1.15M |
| `sc_host_pe` | 1.51M | |
| `rl150_p10000000` | 1.46M | |

  That is ~12k pairs/s per thread, against ~62k per thread for a real sample at 32 threads (2026-10-06 cluster runs).
  The short reads use the extra cores poorly.

**Streamed against written** (the same read setup):

| Read setup | Written | Streamed | Change |
|---|---|---|---|
| paired-end rl150 | 1.46M pairs/s | 0.96M pairs/s | −34% |
| paired-end rl250 | 0.89M pairs/s | 0.64M pairs/s | −28% |
| single-end rl150 | 1.84M reads/s | 2.08M reads/s | none lost |

The streaming simulators ran with `-t 120` beside protal's 120 threads (`stream_pe.log`). Their reads came at ~2M per
second either way, which is what limits a pair. Streaming was needed because the scratch disk had 527 GB free: 21 of the
116 simulations streamed (~518 GB of reads).

**Small samples:** at each read type's large-sample rate, the samples under 20,000 long reads or 2M short reads took
~200 s more than their work. Long reads lose most of it (ONT 97 s, PacBio 62 s): a sample of 38 ONT reads cannot
occupy 120 threads.

**Profiling stages:**
- Training run 2 profiled 1,063 samples in 350 s (v19: 248 s), about 25 at a time.
- The per-sample work summed to 8,798 s against 6,228 s in v19 (+41%):
  - reading the SAMs 4,617 against 3,695 s;
  - record evidence and sample context 3,998 against 2,363 s (+69%);
  - congener distances 3,486 against 1,955 s (+78%).
- This matches the strain-allele and polymorphic-site work added since v19 (`504de80`, `ea6de54`).
- The stage ends with its slowest samples: `sc_soil_shallow_pe_p5000000` and `sc_moderate_pe_p10000000` at 180-220 s
  each.

## 3. How busy the cores were: the idle-priority build as a probe

The finished database was built in the background at the idle scheduling class, which runs only on cores nothing else
wants. Its stages against the training database's, which ran alone on the same node:

| Stage | Training database, alone | Finished database, at idle class | Slower |
|---|---|---|---|
| congener gaps | 8:14 | 1:31:07 | 11.1× |
| suspect copies | 0:20 | 2:22 | 7.2× |
| species neighbours | 0:04.5 | 1:06 | 14.7× |
| strain alleles | 0:28 | 2:59 | 6.5× |
| write the index | 0:43 | 3:34 | 5.0× |
| write database.protal | 1:17 | 18:07 | 14.2× (to NFS) |
| the whole build | 12:16 | 1:58:32 | 9.7× |

- The congener gaps ran from ~12:23 to ~13:54, beside the test set's streamed run, training run 1, the test set's
  written run and the start of training run 2, at 1/11 of the speed they had alone.
- So the protal runs (and until 12:32 the simulations) left roughly 1/7 to 1/15 of the machine idle: **~8-17 cores of
  120, or 86-93% busy.**
- Caveats:
  - The two databases differ a little (10,620 species fewer in the training one).
  - Writing went to NFS.
  - A core busy with a thread waiting on memory, or with an OpenMP thread spinning at a barrier, counts as busy.
- So "busy" here does not mean efficient. For short reads it most likely means stalled on memory (section 2).

## 4. Setup: the NFS steps

| Step | v19 | v21 |
|---|---|---|
| genome table | 9:42 (49,595 genomes) | 8:00 (37,422) |
| converter | 4:04 | 7:23 |
| gene neighbours | 3:18 (49,405 genomes) | 15:37 (37,331) |
| derive | 5:17 | 6:42 |
| training build | 14:41 | 12:37 |

- Gene neighbours read fewer genomes, 4.7× slower. The converter read the same release, 1.8× slower. Both read
  `/hpc-home`, whose speed varies between jobs.
- The training build, which reads only scratch, got 14% faster.
- At `79ae8ee`:
  - the genome table and the converter run side by side, and the gene neighbours start once `reference.fna` is written;
  - the in-silico strains run in the background, and the derive runs on all cores;
  - lengths and contig names come from one cached pass.
- The gene neighbours still read every genome from NFS.

## 5. What today's commits change for a build like v21

| Change (commit) | v21 time it addresses | Expected saving |
|---|---|---|
| ONT: the indel bound in place of the k-mer screen (`0c94366`) | ONT aligning 3,777 s | 30-50 min of the collection (−45% instructions locally; most host candidates unrelated at r226) |
| `--profile-ahead` on (`79ae8ee`) | profiling stages 866 s | ~8-12 min |
| setup graph, parallel derive, genome cache (`79ae8ee`) | setup 53 min | ~10-15 min (more on a rebuild with the cache) |
| reports right after training, no unpack, one ancestry pass, cached contig names (`79ae8ee`) | reports 15 min | ~8-10 min |
| streamed runs merged, the batch chosen after the lock (`79ae8ee`) | 3 streamed training runs | a few start-ups and profiling tails |

Together: **3:15 → ~2:15-2:35** on the same node.

## 6. Recommendations

1. **Run v22 with `79ae8ee` + `0c94366`** and read its CPU logs:
   - `logs/cpu_timeline.tsv` over the collection, idle against busy cores per run;
   - `logs/protal_cpu_<collection>.tsv`, cores busy per sample by read type (does paired-end keep 120 cores busy?);
   - `logs/cpu_jobs.tsv`, the setup steps' cores busy.
2. **The finished database's build may reach the critical path.** At the idle class it took 1:59 and ended at 14:17,
   3 min before the collection. With the collection 30-50 min shorter, part of it will run after. The build then waits
   for it ("waiting for protal_db's build"), at full speed by then, so it adds at most ~10-15 min. Options:
   - give it a fixed share of cores at normal priority (16-24 threads) while the collection runs;
   - write its `database.protal` to scratch and copy it to NFS once (18 min of writing at ~22 MB/s here).

   v22's timeline will show whether it bites.
3. **Streaming simulators: fewer threads.** They ran with `-t 120` beside protal's 120. Capping them at ~16-24 should
   recover most of the paired-end streaming loss (~30% on ~450 s of streamed paired-end aligning, ~2-3 min). A larger
   scratch disk (≥ 1 TB) would avoid streaming altogether.
4. **Short reads at 120 threads** (paired-end and single-end, 1,348 s of aligning, gaining 0-18% from 43% more cores):
   - First measure: one large paired-end sample at 60 and 120 threads, and with `numactl --interleave=all`.
   - If it is memory- or NUMA-bound, two protal processes of 60 threads, one per NUMA node, would raise the short reads'
     throughput (item 7 of the parallelism report, which needed exactly this evidence).
   - If it is reader-bound, more reader threads per file.
5. **Profiling cost per sample grew 41% since v19** (record evidence +69%, congener distances +78%). The largest
   scenario samples take 3-4 min each. `--profile_ahead` hides part of it. The congener distances of a large sample are
   the next profiling target, if v22's profiling stages stay long.
6. **NFS in the setup:** gene neighbours read every genome again; staging the inputs on scratch once (or reading them
   through the genome store) would make the setup independent of `/hpc-home`'s speed.

## Reproducing

```bash
# per protal run, per read type, per design point (v21 and v19)
bash docs/claude/2026-10-09-build-parallelism/scripts/run_timings.sh local/v21/protal0.7.9_r226_v21/logs
bash docs/claude/2026-10-09-build-parallelism/scripts/run_timings.sh local/v19/protal0.7.9_r226_v19/logs
# the idle-priority build against the training build, stage by stage
grep -E "took" local/v21/protal0.7.9_r226_v21/logs/training_db_index.log
grep -E "took" local/v21/protal0.7.9_r226_v21/logs/index_and_package.log
# training run 2's profiling stage, summed by component
awk '/^==> run2 <==/{on=1} /^==> run3 <==/{on=0} on' local/v21/protal0.7.9_r226_v21/logs/protal_runs_training.log |
  perl -ne 'if (/^Profiling sample \S+ took ([\d.]+)s: (.*)/) { $n++; $t += $1; for (split /, /, $2) { $c{$1} += $2 if /^(.*?) ([\d.]+)s$/ } }
            END { printf "%d samples, %.0f s\n", $n, $t; printf "  %s %.0f\n", $_, $c{$_} for sort { $c{$b} <=> $c{$a} } keys %c }'
# streamed simulations and the protal runs' durations
grep -E "streamed|protal run [0-9]+|protal profiled" local/v21/protal0.7.9_r226_v21/logs/{training,test}_data.log
```

`local/` is not in git: the unpacked `protal0.7.9_r226_v21_share.tar.gz` and `..._v19_share.tar.gz`.
