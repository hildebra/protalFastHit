# Speed of protal 0.8.5 at GTDB r226 (cluster run Perf0.8.5)

Date: 2026-10-17. Branch `audit-fixes`.

- **Cluster run:** protal 0.8.5 at `830a92b`, the user's job as `local/Perf0.8.5` (`environment.txt`; the job printed
  its output folder as `runs/Perf0.8.2/`, a reused name):
  - SLURM 24300272 on q512n17 (AMD EPYC 9634, one socket, one NUMA node, 84 cores, 502 GB), 32 threads, transparent
    huge pages `always`.
  - Database: r226 v24 (`protal0.8.1_r226_v24`, 30 GB, on NFS): no gates, no grid levels, ungated models only.
  - Run folder on the node's SSD (ext4), as in Perf0.8.4d/e; Perf0.8.4a-c wrote to NFS.
  - Samples as in every run since 0.7.5: pe1 (PEARL_AGE B10, 50.6 M pairs, gzip of 290,592 members per file), pb2 (one
    HiFi barcode, 497,656 reads), ont3 (soil ONT, 3.10 M reads); the long-read files are single-member gzip.
- **What it ran:** `scripts/measure_performance.sh --test_sparse`, three repeats per sample, the cohort (qcMSA on), and one
  run per gate: `--sparse_first` 1, 2, 4, 8 (pe) and 4, 8, 16, 32 (long reads), with the database's pick. v24 records
  none, so that is the stride pick on the whole index. No comparison profiler, no stage-1 probe.
- **0.8.5 against 0.8.4:** the key map is the hashed one by default (`4cf4f75`, built in 0.29 s here). The F1-audit
  fixes since `55f850d` change the work a little: pe looks up 3.6 M fewer k-mers (most likely those over an N, F1 audit
  L10) and writes 873 fewer records (−0.04%). HiFi and ONT do the same work as 0.8.4, to the last k-mer, seed, anchor and record. New is
  the spike-gene check before each profile (`--spike_genes auto`).
- **Earlier runs compared:** from the report of 0.8.4
  ([2026-10-15-perf-0.8.4a](2026-10-15-perf-0.8.4a/README.md)) and its data in `local/`:
  - 4a: `5369c99`, compact key map, NFS run folder, q512n20;
  - 4c: `8d528aa`, `--direct_keys`, NFS run folder, q512n23 (numbers from that report's tables);
  - 4d: `4d89d86`, hashed map without the build fix, SSD, q512n12;
  - 4e: `55f850d`, the fixed hashed map, but on a two-socket node (q1536n4), so not comparable in absolute times.
- No new runs were made for this report. The numbers are read from `runs.tsv`, `stages.tsv`, `sparse.tsv`,
  `sparse_stages.tsv` and the logs with awk.

"Warm" means repeats 2 and 3. The script's printed medians include the cold repeat 1: pe's median (37.45 s) is
repeat 2.

## Summary

- **0.8.5 is the fastest 0.8.x on all three read types.**
  - Warm pe: 34.3 s (repeat 3; repeat 2 took 37.5 s, its start-up 3.2 s slower, see section 1).
  - HiFi: 11.5-12.0 s. ONT: 49.8-49.9 s.
  - Peak memory: 36.0-36.7 GB, between the compact map's (35.1-36.2) and the direct map's (37.6-38.5).
- **The hashed key map works as intended:**
  - It is built in 0.29 s (3.6 s in 4d).
  - pe seeding takes 177 ns a lookup: compact 197, direct 166.
  - Relative to anchor extension (the same node's memory speed), its seeding is within 1% of the direct map's for pe,
    +3% for HiFi and −2% for ONT.
  - The hashed default can stay. The one-node A/B of all four maps (`keymap_ab_job.sh` of the 0.8.4 report) has not
    been run. It would only settle the last ±3%.
- **At the stride gates, pe is at its best:**
  - pe C 4: 19.3 s, records −0.20%. That is −44% against warm repeat 3.
  - HiFi C 16: 9.0 s. ONT C 8: 34.4 s (C 4: 33.4 s).
- **Not measured: the grid pick and its sparse index at r226.** v24 has no grid levels. The grid pick has been the
  GTDB build's default since 2026-10-16, so `--test_sparse` now times grid levels by default (section 7). The next
  run needs a database built since 2026-10-13, e.g. v31.
- **Where a gated pe run's time goes** (C 4, 19.3 s):
  - aligning: 9.5 s;
  - profiling: 5.1 s;
  - start-up: ~4.1 s.
  
  Within the profiling, the new spike-gene check reads the whole SAM a second time: 0.72 s per pe sample, 3.7% of the
  gated run (section 4).
- **Gated long reads still wait for their gzip input:**
  - HiFi C 16 spends 46% of its aligning getting reads.
  - ONT C 8 needs 13.6 s of CPU per alignment thread, but its alignment takes 28.3 s. Its stage timers account for
    only 14.7 s per thread. The rest is in no timer, and only in gated ONT runs (section 4).
- **The first run of a sample is still dominated by NFS:**
  - pe repeat 1 took 607 s: the database came from NFS at 61 MB/s (index 494 s).
  - The cold reads held the alignment back by 81 s a thread (pe) and 90 s (ONT).
- **Calls:** ONT's gated calls differ from its ungated ones at every gate (Bray-Curtis 0.14, 17-28 species gained), as
  in every run on v24. v24 has no gate models; this is a scoring question, not a speed one.

## 2. The hashed key map at r226 on a single-socket node

Warm means. Seeding ns a lookup = seeding thread-seconds over the k-mers found in the index.

| | compact (4a) | direct (4c) | hashed v1 (4d) | **hashed, next line too (0.8.5)** |
|---|---|---|---|---|
| hashed map built in | – | – | 3.57-3.68 s | **0.29 s** |
| pe seeding, s per thread | 13.72 | 11.56 | 12.44 | **12.27** |
| pe seeding, ns a lookup | 197 | 166 | 179 | **177** |
| HiFi / ONT seeding, ns a lookup | 173 / 221 | 156 / 205 | 164 / 212 | **161 / 208** |
| seeding / anchor extension, pe | 6.45 | 5.72 | 6.06 | **5.77** |
| seeding / anchor extension, HiFi | 4.64 | 4.22 | 4.48 | **4.35** |
| seeding / anchor extension, ONT | 5.29 | 5.01 | 5.11 | **4.93** |
| pe cache misses (G) | 33.14 | 29.49 | 29.63 | **31.52** |
| gate, ns a sampled lookup, C 1 / C 4 | 144 / 164 | 121 / 117 | 138 / 129 | **144 / 135** |
| pe aligning at C 4, s | 10.00 | 9.02 | 9.22 | **9.50** |
| pe peak, GB | 35.1 | 37.6 | 36.0 | **36.0-36.3** |

- **The nodes differ by a few percent.** This node extended anchors at 2.125 s a thread for pe, against 2.054 s on 4d's
  node and ~2.02 s on 4c's (from that report's ratio). That is why seeding is compared per second of anchor
  extension, a stage that reads memory but not the key map. In the 0.8.4 report the two compact runs on different
  nodes agreed within 0.5% on that ratio.
- **By that ratio, the hashed map is within 1% of the direct map for pe,** 3% above it for HiFi and 2% below it for
  ONT. Raw, pe seeding is 6% above the direct map's (12.27 against 11.56 s), on a node 3-5% slower at extension.
- **The next line costs misses, not time:** prefetching the line after the home line adds 1.9 G cache misses for pe
  (31.52 against 29.63 G in 4d), but the lookups got faster (177 against 179 ns).
- **The gate's lookups gain less than the seeding's.** At C 1 they cost what they did with the compact map (144 ns);
  at C 4, 135 ns against 164 (compact) and 117 (direct). The gate reads one key and a few cells per core; seeding
  scans a block of ~70 cells, so the key map is a smaller part of each lookup there. In gated pe, the hashed map
  costs ~0.5 s of aligning against the direct map (9.50 against 9.02 s), for 1.3-1.6 GB less memory.
- **Verdict:** section 11's rule of the 0.8.4 report is met. The build is under 0.7 s, and pe seeding is within ~4% of
  the direct map's when normalized (not raw). The hashed default stays. The four-map job on one node
  (`docs/claude/2026-10-15-perf-0.8.4a/scripts/keymap_ab_job.sh`) would settle the remaining ±3%, but no longer
  decides anything large.

## 4. Where the time goes at the gates

Seconds per alignment thread (the stage timers), one run each. The rows with a dot are parts of seed- and
anchor-finding for pe and of the alignment handler for the long reads.

| stage | pe1 C 4 | pb2 C 16 | ont3 C 8 |
|---|---|---|---|
| aligning (wall) | 9.50 | 3.94 | 28.29 |
| getting reads | 1.17 | 1.80 | 4.18 |
| retrieving k-mers (short reads) | 1.59 | – | – |
| seed- and anchor-finding (short reads) | 4.24 | – | – |
| alignment handler (long reads: all their work) | 1.30 | 2.01 | 10.47 |
| · the gate ("Sparse first") | 2.50 | 0.39 | 1.85 |
| · seeding the kept reads | 1.09 | 0.49 | 1.84 |
| · sorting seeds, pairing, extending anchors | 0.75 | 0.38 | 1.45 |
| · indel bound (ONT) | – | – | 3.73 |
| anchor recovery, joining and sorting pairs (pe) | 0.63 | – | – |
| output handler | 0.55 | 0.03 | 0.05 |
| **timed in all** | **9.47** | **3.84** | **14.71** |
| alignment CPU / 32 (cpu.tsv, with the inflate threads) | 11.2 | 2.6 | 13.6 |

- **pe and HiFi are fully accounted:** their timers sum to the alignment's wall time.
- **ONT gated runs are not.** 13.6 s per thread of C 8's 28.3 s is in no timer: 9.2 s at C 4, 10.8 s at C 16, 11.9 s at
  C 32.
  - The ungated ONT runs are accounted.
  - The alignment threads leave their loop only when the reader returns no more reads, and the loop body is timed
    throughout (`Classify.h` RunLongReads).
  - So either the reader's sampled timer (every 61st call, `Benchmark::kPerRead`; the waits fall in the one call of
    32 that refills a thread's batch under the shared lock) underestimates the waiting, or threads finish at very
    different times.
  - The input bound alone explains the wall time. At ~6.8 bp a lookup, ont3 is ~11 Gbp, ~22 GB of FASTQ; read in
    28.3 s, that is 0.78 GB/s, the single-member gzip rate the 0.8.4 report measured (lead-bound ParallelGzip).
  - What is not explained is why the timers do not show it.
- **Gated pe: profiling is now half of the alignment.**
  - Profiling took 5.1 s: spike genes 0.72 s, reading the SAM 2.52 s, record evidence 1.38 s, read EM 0.62 s,
    congener distances 0.23 s.
  - The SAM read is as in 0.8.4: the reading thread waits 1.27 s for room, and the main thread spends 0.79 s alone
    adding the chunks' counts.
- **The spike-gene check reads the SAM twice.** `Profiler::CountGeneRecords` (`Profiler.h`) decompresses and scans
  the whole SAM (1.73 GB of text for pe) before the profiling's own read, to count each gene's primary mapped records
  (`spike_genes::CountRecords`).
  - Cost: 0.72 s for pe, 0.12 s for HiFi, 0.15 s for ONT. On every sample, also when no sample is in spike mode (none
    of these is).
  - The alignment writes those records itself. It could count them as it writes and hand the counts to the profiling
    of the same run; only a profile of an existing SAM (`--profile_only`, a reused SAM) would need the extra pass.
- **Start-up of a gated pe run, ~4.1 s:**
  - index load 3.41 s (the hashed map 0.29 s of it), beside the genome preload (1.78 s) and the tables;
  - after the profile, freeing memory 0.27 s.
  
  A map of many samples pays this once.

## 7. The script: `--test_sparse` now times the grid pick

At the user's request, `measure_performance.sh --test_sparse` now measures grid-based gates by default.

- **Default levels:** `2g 4g 8g 16g` for short reads and `4g 8g 16g 32g` for long reads (were `1 2 4 8` and
  `4 8 16 32`, the database's pick on the whole index).
- **What a `g` level runs:** `--sparse_first C --sparse_first_pick grid` with protal's `--sparse_index auto`. It loads
  only the entries of grid level log2 C or more, so it times the sparse index's memory, load and lookups. GTDB builds have
  gated this way by default since 2026-10-16 (`aa7c0e6`).
- **On a database without grid levels** (built before 2026-10-13, like v24), protal stops with exit 2.
  - protal reads the index's features only after its gene tables, so the script cannot ask before a run.
  - Instead it reads the first run's "Index features:" line. Without grid levels it leaves the `g` levels out, with a
    warning on stderr, a line in `environment.txt` and a note at the end. The timed runs and the cohort still run.
- **The old measurement:** `SPARSE_SHORT="1 2 4 8" SPARSE_LONG="4 8 16 32"`. Plain levels still gate with the
  database's pick on the whole index, `s` levels with `--sparse_seeding`, and `0` is ungated.
- **Checked:** a dry run in WSL with a stand-in protal (scratch only, not kept). On a database with grid levels, every
  `g` run got `--sparse_first_pick grid`. On one without, the `g` levels were left out after the first run, with the
  three messages. With `SPARSE_SHORT="1 4g" SPARSE_LONG="8"`, levels 1 and 8 still ran.
- **Docs:** `docs/development.md` and `docs/version_changes.md` (since 0.8.5).

## 8. What to do next

1. **The next cluster run on a database with grid levels** (r226 v31 or the next build): the same samples, the run
   folder on the node's SSD, with the new defaults:

   ```bash
   export RUN_DIR=/nbi/local/ssd/$SLURM_JOB_ID/perf
   bash scripts/measure_performance.sh --threads 32 --test_sparse OUT_v31 DB_v31 pe:R1:R2 pb:R ont:R
   ```

   - It gives the sparse index's peak memory and load time at r226 for the first time. Expected: about 1/C of the
     index's 26.6 GB of entries, the key map aside; the local mock database was too small to show it (2026-10-14).
   - v31 picks by stride and its models were trained on stride rows, so the `g` runs' calls are only indicative. Their
     records and speed are what a grid-built database gives.
   - v31 records its gates (pe 4, HiFi 16, ONT 8, stride), so the timed runs are gated there; `SPARSE_SHORT="0 2g 4g
     8g 16g"` (and `0` for the long reads) adds an ungated run.
   - In the same job, `PROTAL_INFLATE_THREADS=16` for the long reads (the 0.8.4 report's 6.1(a), still not run). The
     gated long reads wait for their gzip input, and the model there predicts +40% input speed.
2. **Count the spike genes during the alignment** (section 4). This saves 0.7 s per pe sample (3.7% of a gated pe
   run) and 0.1-0.15 s per long-read sample. The counts must equal those of the SAM pass: primary, mapped records by
   (taxid, gene). **Done the same day:** [2026-10-17-spike-count-in-alignment](2026-10-17-spike-count-in-alignment/README.md).
3. **Find gated ONT's untimed 13.6 s a thread** (section 4):
   - time the reader's refill (the lock and `LoadBatch`) on every call; it is one call in 32;
   - log the spread of the alignment threads' end times.
   
   If it is the input, as the wall time suggests, it is 6.1 of the 0.8.4 report (the ParallelGzip lead).
4. **pe profiling's SAM read** (the 0.8.4 report's 6.3, unchanged): 1.27 s waiting for room and 0.79 s of
   single-threaded adding per pe sample.
5. **The key map:** keep the hashed default. The four-map job settles the last ±3% if wanted.
