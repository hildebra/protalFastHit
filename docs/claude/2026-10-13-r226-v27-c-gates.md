Data: the r226 v27 build (SLURM 24220601, 120 threads, node q1536n3). The command was

## What the table measures, and a flaw in its F1

Each read type's test samples are profiled again at the other gates in the same protal run, as `<sample>__c<C>` rows.
The model trained at the database's gate scores those rows (the trainer's `extra_tests`). Samples streamed through
pipes have no rows at other gates. That leaves out the deepest scenario samples: gut, moderate, soil and host for pe,
pb and ont, 16-20 samples per read type. The rows cover 81 pe, 89 se, 42 pb and 42 ont samples.

The trainer scores the rows of each table. A present species that has **no row** at a gate counts neither as TP nor
as FN, so `present` (= TP + FN) shrinks as the gate rises. pe at C 4 by hash has 11,715 present against 11,732 at the
other gates. Its 17 species without a row leave the denominator, so its F1 in `c_gates.tsv` rises (0.94332). Counted as
FN, they give 0.94263. These vanished species are mostly ones that C 1 does not call either: TP is 10,918 at C 4 with
both picks, and 10,904 at C 1. Their cost to F1 is small, but they are what the gate loses, and the hash loses many
more of them than the stride does.

Below, "fair F1" counts as FN every present species of the same samples that has a row at some gate (the read type's
largest `present`) but none at this gate:

```bash
awk -F'\t' 'NR>1{k=$1":"$6; if($8>U[k])U[k]=$8; r[NR]=$0} END{for(i=2;i<=NR;i++){split(r[i],a,"\t");
  k=a[1]":"a[6]; fn=a[11]+U[k]-a[8]; print a[1],a[2],a[3],a[4],U[k]-a[8],2*a[9]/(2*a[9]+a[10]+fn)}}' c_gates.tsv
```

One species moved between FN and TP changes F1 by about 4.6e-5 (pe), 2.7e-5 (se), 9.0e-5 (pb) or 8.7e-5 (ont).

### The gates

- Up to the largest gate tested, the gate costs no measurable F1: pe and se to C 4, pb to C 16, ont to C 8. Across all
  gates and both picks, fair F1 stays within 0.001 of the database's gate for each read type, at most about 35
  species out of 6,000-19,000. Turning the gate off is no better: pe 0.9424, se 0.9588, ont 0.9544, against 0.9431, 0.9597
  and 0.9542 at C 1. These models were trained at C 1, so their runs with the gate off are the mismatched ones.
- CPU falls steeply. C 1 alone saves 19-25% against no gate for pe, se and ont. Against C 1, C 4 saves another 36-44%
  for pe and se and 25-27% for ont, and C 8 saves 36% for ont. For pb, C 16 saves 11% against its database gate of C 8.
- Every row other than the database's is scored by a model trained at the database's gate, so a mismatch is included
  in these numbers. pe's FP rise from C 1 to C 4 is 488 → 515 with the hash and 488 → 497 with the stride.

### Hash against stride

- **The stride loses fewer present species in all 9 pairs.** pe C 4: 1 against 17. se C 4: 3 against 27. pb C 16:
  2 against 10. ont C 8: 5 against 17. This is what the probe predicted
  ([stride pick](2026-10-13-stride-pick/README.md): records lost locally at C 8, 0.62% against 7.97%).
- **Fair F1 is equal or higher with the stride in 8 of 9 pairs.** The exception is ont C 4, by 0.0002 (about 3
  species). The largest gains are pe C 4 (+0.0007, 18 fewer FP) and se C 4 (+0.0005, 24 fewer FN). Each difference is
  at most about 20 species, too small to call alone; that the direction repeats is the signal.
- **CPU:** short reads are 1-5% cheaper with the stride. Long reads are 3-5% dearer at C 4 (pb 962 against 915, ont
  748 against 728) and within 2% at C 8 and 16. The stride keeps reads that the hash gives up, and those reads go on to be
  aligned. At C 4 these differences are probably within the noise of concurrent rows.

### --flex_indels (in passing)

- ONT: no F1 gain at any gate (fair F1 within ±0.0003 of the same gate without it), and 16-19% more CPU at C 1-8.
  The model was trained without it.
- Ultima (12 se samples): fair F1 0.9582-0.9589 at C 0-4, with the same samples at C 1 without it at 0.9587 (that
  row's present count is not in the table). There are no rows of these samples at C 2 or 4 without it, so its cost
  per gate cannot be separated from the gate's.

## Conclusions

1. The gate works. At r226, C 4 for pe and se, C 8 for ont and C 16 for pb cost no measurable F1 on these samples, and
   save 36-44% of the alignment CPU against today's database gates (pb: 11%).
2. The stride pick is the better pick: it loses 2.5-17× fewer present species, and its F1 is equal or better. This
   meets the condition set for a rebuild with the stride on ([stride pick](2026-10-13-stride-pick/README.md)): at
   least the hash's recall and F1, at no higher cost.
3. A rebuild with the stride, and the models trained at it, needs:
   - a build option that passes `--sparse_first_pick` to both databases' `--build`. `build_gtdb_database.py` has none
     yet. The test rows must then set the hash explicitly where they want it (`SPARSE_FIRST_PICK=hash`), because a
     row without the column follows the database's pick.
   - gates for that build. A proposal: `pe:4,se:4,pb:16,ont:8`, all by stride, tested at
     `pe:0/1/2/8,se:0/1/2/8,pb:0/8/32,ont:0/1/4/16` with the hash at the same gates for comparison. That covers the
     untested C 8 for short reads and C 32 for HiFi.
4. Before trusting high gates on deep, complex samples: none of the streamed scenario samples (soil, moderate and gut
   at 10-20M pairs, 3-6 Gb of long reads) have rows at other gates. The rebuild's scenario hold-out F1, against v27's
   (soil pe 0.953, pb 0.968, ont 0.959), is the check for them.
5. `c_gates.tsv` should count present species without a row as FN, or carry a `present_lost` column. As it is, the
   F1 in the table favours whichever pick loses more species.

## Follow-up (same day): what was changed

The user asked for points 1 and 3 and more (all uncommitted at writing, on `0ab85f4`):

- **The stride by default.** `protal --build` records the stride pick for every read type unless
  `--sparse_first_pick` says otherwise. A run follows its database's pick: stride where it records none, hash for a
  database that records its gates but no pick (built 2026-10-12/13, its models trained by hash; `DatabasePick`).
- **Gates.** `build_gtdb_database.py --sparse-first` defaults to `pe:4,se:4,pb:16,ont:8`, and `--sparse-first-pick`
  (default `stride`) passes the pick to both databases' `--build`.
- **Models at several gates.** `--model-gates` (default `pe:1/4/8,se:1/4/8,pb:8/16/32,ont:1/8/16`) profiles both
  collections at each other gate too. The collector's `--model_levels` includes the streamed samples: each streamed
  simulation is streamed again per gate by a simulator of its own. A model is trained at each gate and stored as
  `model_<type>_c<C>.xml` (`protal --add_model --model_gate C`; the finished database's build packs placeholders, so
  `--add_model` replaces them in place). protal profiles each sample with the model trained at the gate nearest its
  own (`NearestGate`: log2 C, off next to 1, the lower of two) and warns only if that gate is not its own.
- **`c_gates.tsv` fixed.** The collector writes `<table>.unseen.tsv` for every gate's table. The trainer's extra tests
  count those species as FN (`unseen`), and each level is scored by the model of its nearest gate (`model_gate`).
  New columns: `pick`, `model_gate`, `unseen`. The other pick is tested by `--test-other-pick` (hash rows `__c<C>h`
  beside a stride database), by default at the database's gate.
- **Not done: a hash-based sparse index** (load 1/C of the keys). It cannot serve the stride pick. The user chose the
  stride with the full index; a gene-position grid index (every C-th core of each gene kept at build time) is the
  idea to work out next.

Verification (WSL, 4 cores, the working tree): C++ unit tests 555 pass, end to end 176, the collector's, build's
and trainer's script tests 102, and the mini GTDB pipeline 8 (test_j trains pe at gate 1 beside the database's 4 by
stride, and checks c_gates.tsv, summary.txt and the packed model_pe_c1.xml). The pipeline ran before the last two
small protal fixes (the warning's wording, a model given for several read types loaded for each), which the unit and
end-to-end tests cover. No r226 build with these defaults has been run yet.
